# Canonical planetary generation and multi-seed world identity

Status: **approved architectural direction and owner policies (2026-10-21), documentation-only; future universe/catalog and multiplayer implementations are not shipped by this document**. This is the authoritative contract for stable, versioned base-world identity; the current compressed six-body prototype and its version-1 terrain/resource generators retain their existing behaviors until deliberately migrated. See [approved universe expansion](universe-expansion-approved-design.md), [world and realism](world-and-realism.md), [terrain contract](../client/world/terrain-contract.md), [resource contracts](../client/world/resource-contracts.md), and [multiplayer](multiplayer-and-npc-interaction.md).

## Player-visible invariant

A planet or moon has **one shared canonical base definition**, independent of player, client process, session, device, load order, and whether its data is read from the installed offline universe package or later from the authoritative backend. Two players visiting the same location must encounter the same underlying mountains, canyons, craters, natural resource identities and designated fixed discovery sites. Terrain patches, render LOD, streaming order, and local graphics settings may vary, but must not alter physical world identities, collision geometry or what is canonically present.

No generation step may obtain a fresh player-specific, time-of-launch, process-random, unordered-iteration, or system-clock seed for **immutable base-world content**. "No runtime randomness" here means **no nondeterministic or uncommitted world-identity decisions at runtime**; the engine may evaluate deterministic noise, hashes, and fixed-seed pseudorandom samplers on demand from a published canonical definition. This preserves current resource sampling (FNV-1a / SplitMix64) and terrain evaluation (hash-based lattice noise). Dynamic, time-varying simulations are separate from immutable geography and must use their own synchronized/authoritative state.

## Canonical planet record and independent seed domains

Each future planet has:
- **Stable canonical body ID**, disjoint from display name, catalog ordering, runtime indices and existing compressed-prototype enum discriminants.
- **Revision-immutable physical and astronomical inputs** as relevant (radius, identity, provenance, observational validity) and a versioned planet record/schema. An explicit approved migration can publish a replacement revision; runtime generation never mutates the active revision.
- **Published multi-seed map**, with independent named domains and their evaluation/algorithm versions. The seed representation and derivation must be a reproducible, platform-independent binary/packed contract; it need not be a free-form seed string. A reproducible root seed **may** be used by the offline pack builder to derive distinct domain seeds, but the resulting per-domain seeds and versions are part of the canonical record. Use explicit domain separation, fixed byte ordering and a specified stable hash/PRF; never rely on default language hashers or a mutable RNG sequence.
- **Full canonical-definition content digest** and preferably subsystem-specific digests for exact validation/cache invalidation; a seed alone is not a sufficient cache or compatibility key.
- **Authored overrides and provenance** where a scientific source or designed location takes precedence over procedural proposals. Versions and overrides are part of the definition/digest.

Proposed domain breakdown (implement only when the respective system is designed):

| Domain | Owns | Separation rule |
| --- | --- | --- |
| Terrain | One **authoritative** sampled height/surface/collision definition for each body/revision | Consumes versioned geological landform inputs; rendering, landing, walking and resource anchoring use its same physical query |
| Geology | Higher-level landform, substrate and physical composition descriptors when introduced | **Input to terrain/resource systems**, never a second independent physical surface or render-only collision displacement |
| Resources | Stable deposit lattice, resource selection and original deposit IDs | Independent sampler seed, but explicitly consumes approved biome/geology/material inputs; intentional distribution changes require versioned resource identity/depletion compatibility |
| Visual | Planet color/texture/material recipes and safe purely presentational variation | Cannot determine collision, resource or gameplay identity; renderer LOD remains local |
| Biomes / ecology | Future environmental regions and baseline biological distribution | Independently seeded, but may be an **explicit dependency** of resource distribution; biome keys cannot depend on player position/session randomness |
| Discoveries | Future canonical natural/artificial site placement and stable site IDs | Authored site overrides and rare-event placement are shared, not per-run random rewards |

A domain's seed **does not by itself** define its output. Bind its algorithm version, parameters, authored feature set, scientific-input provenance where applicable, explicit **upstream domain dependencies**, and stable identities into its versioned definition. **Seed independence prevents accidental coupling, not intentional physically meaningful coupling:** merely adding an unused domain or reordering generation must never reshuffle another domain; explicitly making terrain consume geology, or resources consume biome/geology, can intentionally change those outputs **only in a newly published compatible revision**, with saved identity/delta migration where needed. Consumers must resolve versioned inputs consistently on every platform and use the same canonical terrain query for physical interactions. Do not assume new geology, erosion, vegetation, dynamic weather or discoveries are implemented today.

For the existing version-1 terrain implementation, the validated `TerrainDefinition` already includes `u64` seed, generator version, radius, ordered layers and sparse authored features; retain that exact code/codec contract. Existing resources derive stable per-material inputs via FNV-1a and fixed SplitMix64 lanes. Do not silently rekey currently saved deposits/fixtures or treat the current six-body tag codec as the future galactic body-ID format.

## Offline package and future backend: one data contract

1. A reproducible **offline catalog/pack builder** selects/derives fixed parameters and seeds for fictional populations and writes the published canonical record and digest. Generation for a new catalog version happens during content production, **not independently for each player at runtime**. For **real observed bodies anywhere in the catalog**, favor measured scientific/geographic data where practical, with source provenance and versions; unknown details may still be approximated deterministically before first authoritative publication, but subsequently follow the real-body preservation policy below.
2. The client reads canonical records from the **installed versioned universe pack**, and only evaluates their expensive local procedural geometry/resources/visual recipes on demand. This is not a requirement to store full meshes or entire heightfields in the package.
3. In future multiplayer, a backend database/catalog serves **the same canonical definitions** (or authenticated digest + version/ID referencing an exactly matching local record). It owns definition publication/compatibility and gameplay authority; it does not independently invent new terrain when a player arrives. Never silently accept mismatched client/server definitions.
4. Catalog/version IDs and full definition digests flow into caches and saved state. On missing/unsupported/mismatched definitions, fail clearly, request a compatible published catalog, or run an **explicitly approved migration**; never quietly reinterpret a visited world.
5. A canonically published planet is **immutable within its definition revision**, but **approved controlled migrations may update already published fictional planet geography** (owner decision B). A migration publishes a new versioned definition and digest, provides validated coordinate/entity/delta compatibility, and changes the canonical active revision for every player together. Never silently reinterpret a visited planet or allow old/new clients to interact against different active physical surfaces. If existing landmarks, players, deposits or deltas cannot be safely migrated, the change must be redesigned, deferred or rejected; offer explicit fallback/rollback behavior. The new revision must be distributed consistently through the offline package and future backend catalog. See migration policy below.

The source of a definition (package file or database) is an adapter concern, not two separate generators. The future server may validate sampled surfaces/deposits independently using portable Rust world code. Cross-platform golden vectors and collision tolerances, not identical render screenshots, establish compatibility.

## Immutable baseline versus mutable shared world

- **Baseline**: planet identity, canonical terrain and physics surfaces, original deposit IDs/distribution, authored fixed landmarks/discovery sites and baseline environmental descriptors. Query/render it on demand without allocating an entire planet.
- **Mutable state**: consumed/mined resources, moved cargo, wrecks, changed structures, player and NPC actions, and any future terrain deformation. Persist changes as stable-ID deltas and versioned spatial events, authoritative on the backend when multiplayer exists. The existing mining depletion journal is an early local precedent.
- **Time-dependent simulation**: orbit/rotation, weather (if implemented), transient signals, renewable-resource schedules, mobile actors and similar events are not frozen into a planet seed. Their behavior must be consistent with shared simulated time and backend authority; fixed baseline does not mean a frozen scene.
- **Presentation**: mesh density, LOD, cache residency, local shading approximations and quality settings are not part of shared gameplay truth.

Do not infer that planetary bases are approved from the examples above: current [world rules](world-and-realism.md) prohibit permanent player-built planetary bases, with permanent construction limited to spaceships. This architecture supports changes only where separately authorized.

A player's **known navigation/discovery chart** remains separate from the full canonical catalog. Access to a planet record cannot automatically reveal Earth's unknown route, hidden coordinates, unverified signals or narrative evidence in gameplay UI. **Owner decision A:** accept that technically capable players may inspect an installed offline package and discover fixed locations; secrecy is a player-facing gameplay/UI and discovery-state rule, **not** a claim of encrypted or undiscoverable package content. Keep Absenat/Hall spoilers entirely absent from normal pre-completion UI and preserve the Hall's separately approved backend-only shared-endgame contract; no new backend-only location-secrecy requirement is introduced.

## Required future compatibility and validation

- Pack-builder golden hashes across repeated builds, reordered records and machines; canonical serialization, domain separation, collision checks, version rejection and input/provenance validation.
- Compare same planet + same coordinates across Linux/macOS/Windows for sampled heights, normals, physical contact and stable resource/site identities, within explicit numeric tolerances. Current version-1 terrain allows defined floating-point tolerances, not unconditional bitwise equality.
- Verify that changing only visual seed/palette cannot change terrain, collision or deposits; adding an **unused** biome/geology domain or reordering inputs does not reshuffle resource IDs, while a **declared resource dependency** on changed biome/geology inputs requires a versioned publication and stable-ID/depletion migration tests. The same published definition must behave identically after eviction, save/load, offline reopen and multiplayer reconnect.
- Test deliberately mismatched client/server catalog/algorithm versions; reject silent divergence. Test revision-immutable baseline + depletion deltas against two simulated clients. Simulate an approved fictional-planet revision migration with stable identity, remapped or proven-stable physical anchors, resource/depletion journal continuity, old/new client rejection, interrupted migration rollback, and a verified shared canonical active revision. For **all published real astronomical bodies with authoritative solid surfaces**, separately assert no established terrain/collision/position displacement from detail-only updates; do not apply this freeze to the historical six-body prototype fixtures.
- Treat existing compressed six-body catalog, version-1 body tag and local resource sessions as historical/active prototype contracts, not claims that arbitrary galactic body identities or shared backend are implemented.

## Approved publication and migration policy (2026-10-21)

1. **Published fictional planets — option B (controlled revision migration):** Improved generators *may* update an already published fictional planet, but only through an explicit release/migration plan. Preserve stable planet ID; publish new generator/seed/parameter/authoring versions and content hashes as appropriate. Audit changes to surface geometry, safe landing/contact, structures and persistent wrecks, resource/site identities, depleted journals, scanner/navigation references, in-flight positions, saved games and any future server state. Define a validated mapping or prove coordinates and identities unchanged. A migration that would orphan player state or produce split-world geometry is not permitted. Prior snapshots/revision references remain recoverable for validation/rollback; never simply rerun a new generator against an old checkpoint. The future backend selects a single active shared revision and gates incompatible clients; offline saves/package updates likewise validate and migrate explicitly. No automatic terrain upgrades on ordinary launch.
2. **All published real astronomical bodies — option A extended (non-destructive updates only):** Earth, Mars, the Moon, other Solar System bodies, and any other **real observed solid celestial body** with a published authoritative physical/geographic surface (including relevant cataloged asteroids and comets) keep established geography, terrain/collision and stable player-facing coordinates. This requirement concerns **solid physical surfaces**, not a promise to freeze the time-varying atmospheric appearance of gas giants or the changing observational data of stars. Higher-quality observations may improve source metadata, non-displacing visual detail, material presentation and other non-destructive scientific information, but must not move landmarks, crater/canyon boundaries, collision surfaces, resource sites, player positions or persisted state. Even where original geometry was a deterministic approximation of unknown real topography, **the preservation rule begins with that body's first authoritative real-scale world release**, not today's compressed six-body engineering prototype or prepublication drafts. A physical/geographic remapping of a published real body is **not approved** without another owner decision. This surface policy does not prohibit separate, explicitly versioned astronomical/ephemeris corrections under existing contracts.
3. **Discoveries in offline package — option A (accept inspection risk):** Fixed sites can be recovered by inspecting package assets or definitions. No promise of cryptographic secrecy or backend-only delivery for ordinary planetary discovery placement. Gameplay UI, the player-known chart, scanner and archives still enforce reveal/verification progression. The Hall of Absenat remains undiscoverable in normal pre-completion UI and its shared endgame remains future backend scope.

### Controlled fictional-world migration handoff (future design requirement)

Before a revision goes live, a release/migration plan must identify the old/new definition digests, affected domain dependencies, physical surface and deposit/site diffs, persistent-state migrations and validation results. In multiplayer, coordinate a safe handoff: suspend or gate affected interactions while authoritatively migrating all active and offline character/ship/object positions, landing and interior support, mined/depleted resource journals and discoveries; publish one active revision atomically; require compatible client data; and retain recoverable rollback/checkpoint evidence. Offline package upgrades must validate and migrate saves before resuming an old world; never show gameplay against partially upgraded geometry. The exact maintenance window/online transition mechanics remain future implementation design, not a shipped behavior.

These policies change **future design requirements only**; current terrain-v1 codecs, resource IDs, saves and engine behavior are unchanged by this documentation PR.

## Conflict reconciliation and decision record

| Topic | Existing document tension / gap | Approved resolution |
| --- | --- | --- |
| Backend-generated fictional planets | `world-and-realism.md` historically says fictional planets are generated authoritatively **on the backend**, while the later universe plan commits to a permanent offline package. | **Reconciled**: canonical generation/publication occurs in a reproducible pack-build process now; later backend distributes/validates **the same record** and shared deltas, rather than spawning an alternative planet. |
| "No random at runtime" vs current deterministic sampling | Current resource and terrain implementations use fixed-seed noise, FNV-1a and SplitMix64 during queries. | **Reconciled**: deterministic evaluation on demand is allowed; player/session/time-driven randomness affecting base-world identity is not. |
| Existing resource seeds, visual seeds, terrain seeds | These already have independent derivation and cache contracts; swapping to a new root/seed algorithm could move deposits. | **Reconciled**: preserve version-1 semantics, introduce named domains in a future version, and never silently reinterpret saved IDs. |
| Real observed geography vs generated worlds | `world-and-realism.md` asks for recognizable Earth/Mars terrain where practical. | **Reconciled**: real terrain/geographic sources take precedence for measured worlds; the multi-seed model is especially for fiction and compatible procedural detail. |
| Future world/catalog upgrades | Immutable canonical fiction and explicit migrations coexist with later scientific-data corrections and better generators. | **Approved B**: published fictional planets may change via explicit controlled, all-player-consistent, reversible versioned migration; each individual revision remains immutable. No implicit runtime upgrades. |
| Biome/geology versus resource IDs | Resources already support biome-partitioned generation; an overbroad independence rule would prohibit intentional biome-driven resources. | **Reconciled**: independent domain seeds isolate accidental coupling; explicitly versioned upstream geology/biome inputs may legitimately change resources, with documented dependency digests and migrations for persisted deposit state. |
| Geology versus terrain geometry | Separate named seeds could suggest two competing physical surfaces. | **Reconciled**: geology supplies versioned inputs to exactly one authoritative terrain evaluator used by collision, landing, walking and rendering geometry. |
| Scientific terrain updates | Better scientific data could shift established real planetary surfaces and player state. | **Approved A, extended**: freeze physical geography of **all real observed bodies** from first authoritative real-scale publication; allow non-displacing scientific/visual detail only, not freeze the current compressed prototype. Physical remapping requires a new owner approval. |
| Discovery secrecy in offline pack | Fixed shared site placement is compatible with deterministic generation but a user can inspect packaged data even before discovering sites in-game. | **Approved A**: accept offline package datamining risk; enforce in-game discovery visibility instead of pretending canonical data is hidden from inspection. Maintain Hall pre-completion UI secrecy and independently required endgame backend authority. |
