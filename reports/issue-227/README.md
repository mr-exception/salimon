# Issue #227 — offline GLB compliance, exact optimization and visual budgets

Outcome: opt-in processing is available for generic and scout export, with
reproducible Linux CI audits and production CPU importer parity checks. Checked-in
GLBs, Blender sources and generated spatial/interchange files are unchanged.
Prerequisites #224 and #226 were complete on the starting main revision
`91e0e70`; existing geometry-quality and scout category gates are rerun, including
counted remediation exemptions linked to #244. No exemptions/budgets were loosened.

## Implementation

- Local Khronos Validator `2.0.0-dev.3.10`, pinned npm lock/integrity, no runtime
  dependency. Full before/after diagnostics and hashes in CI artifacts.
- Repository-versioned `exact-v1` compacts JSON and aliases identical binary view
  payloads, preserving every index/name, hierarchy, transform, material and extra.
  Full JSON and per-view byte fingerprint rejects semantic changes. No geometry
  quantization, simplification, animation removal or shader changes.
- Staged candidates must pass Khronos validation and all manifest, #226 quality,
  and registered scout preservation/category gates. All 21 real manifests now
  declare separate Option A visual costs (nodes, full RGBA8 PNG mip memory and
  known consumer draw counts); existing triangle/primitive/material/file/encoded
  image budgets remain enforced independently of spatial policy.
- Generic and scout exporters offer `--glb-profile exact-v1`; profile `none`
  retains bytes with compliance/reporting. Omitting the flag disables the optional
  step. Scout regeneration preserves matching interchange/provenance. CI stages
  candidates only; publication requires explicit export. Failures preserve the
  previous candidate/runtime output.
- CPU tests load candidate bytes through the actual ship, held-item and all 18
  resource importers and compare all imported vertex streams; held-item atlas
  pixels/dimensions also match. Public renderer API/GPU behavior is unchanged.

## Toolchain and sharing assessment

The [pipeline guide](../../models/tools/README.md#profile-and-preservation-boundary)
records the conservative equivalent-toolchain choice and glTF Transform upgrade
boundary. Broader graph rewrites, vertex/texture loss and required compression
extensions need dedicated importer/preservation work. The initial profile avoids
those format changes and keeps replaceable visual recipes/material IDs intact.

Resident resource geometry is already shared per variant, with one indexed
instanced draw per visible variant. For 500 identical fragments the pose buffer
scales, not the immutable mesh; six fragment variants take up to six draws.
GLB byte sharing affects storage only. Cross-variant geometry/material-palette
work is a separate runtime optimization and must retain gameplay contracts.
The cargo-container has no runtime consumer and reports null actual draws;
primitive references are recorded separately. Texture memory estimates exclude
GPU driver overhead and runtime-generated cockpit atlases.

## Limits and follow-up

No Blender regeneration or native visual/performance verification was performed.
Native Apple M1 visual signoff stays separate in #229; CPU byte/contract parity
is not a hardware FPS claim. V1 asset contracts reject animation/rigs and unknown
required extensions rather than stripping them. `exact-v1` additionally rejects
extension-bearing assets. Existing #244 geometry remediation remains separate.
Option B can use explicitly reviewed visual budgets while retaining the same
meter-space, collider, anchor and interaction contracts.
